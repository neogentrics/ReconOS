The Gateway, read a second time -- 18 September 2026
====================================================

`scripts/read-intel-display.sh`, run as root on the Gateway (Neo-Gateway, Kali
rolling, 8086:3185 GeminiLake) over SSH from the graphics session.

**This run has the register dump and the first one did not.** The first run,
in `intel-gen9-gateway.txt`, was made before `intel-gpu-tools` was installed --
and then a second time after it was, where the dump came back empty because
`intel_reg read` does not know the register names this script asked for and
says so by exiting 0 and printing nothing (GX-015). That file is kept as it is;
this one is not a correction of it but the same script with a register section
that reads addresses.

Three things to know before reading the numbers:

1. **The panel is on transcoder EDP, not on pipe A's transcoder.** Everything
   at 0x60000-0x60014 reads zero on a machine whose screen is lit. The mode is
   at 0x6F000, and the enable bit is in TRANSCONF_EDP at 0x7F008. GX-013.

2. **A compositor was running.** `mudpuppy` was logged in on tty1 under KDE
   Wayland, so `PLANE_CTL_1_A` and `PLANE_STRIDE_1_A` describe the buffer
   *KDE* allocated -- Y-tiled, stride counted in 128-byte units -- and not the
   fbdev buffer whose stride is the 5504 bytes reported further up this same
   file. Those are two different buffers and comparing them as though they
   were one is a mistake this project made for about ten minutes.

3. **PLANE_SURF moved between the two runs** (0x01500000, then 0x01e00000).
   That is a page flip, and it is the clearest evidence in the file that these
   are readings off a live machine rather than a static description of one.

What it settles, against `kernel/core/intel_modeset.c`: every offset *within*
a block is right, every value this project computed from the connector's
timings appears exactly, and the block itself was the wrong one.
